# Kairoz 原型架构说明

## 1. 定位

Kairoz 是数据采集平台的**可运行产品原型**：全部业务状态和规则运行在浏览器里，用来让各角色完整走通协作流程、验证产品设计。它不是生产后端：没有服务器、数据库或部署；车辆、仿真器、OTA Agent、整车 OTA 系统、仿真服务、Grader、云端处理、质量检查、用途授权与公司人事目录都由“车辆模拟器”扮演。

需求来源是原型 v0.13 的中文设计文档。旧原型代码只作行为参考，不复用。早期的 Node + Postgres 切片（分支 `slice-1-foundation`、`slice-2-dcl-intake`）已停止，规则迁移到了本原型的 `src/domain` 与 `src/engine`。

## 2. 技术栈

| 层 | 选择 |
|---|---|
| 界面 | React 19、Ant Design 6、Vite 8 |
| 状态 | immer 事务；整份状态保存在 localStorage（`kairoz.state.v1`），会话单独保存；保存失败时页面顶部提示，读不出的已保存状态另存（`kairoz.state.unreadable.v1`）后载入演示数据 |
| 摘要 | `@noble/hashes` 的 SHA-256（内容寻址与配置摘要） |
| 语言 | TypeScript 7，只用可擦除语法，Node 24 直接运行测试 |
| 测试 | `node:test`，只测规则与引擎，不依赖浏览器 |

## 3. 结构

```
src/domain/   纯规则：授权、词汇表、触发表达式、数据源与 glob、配置差异、三方合并、摘要
src/engine/   平台：状态类型、各模块操作、演示数据、模拟器
src/app/      持久化、会话、路由、外壳、hooks
src/pages/    各角色页面
src/i18n/     中英文
```

- **一次操作一个事务。** `engine.run(username, ctx => op(ctx, …))` 在 immer 草稿上执行；抛出异常则整次丢弃。操作先 `ctx.allow(action, target)` 授权（允许的决定写审计），再做业务规则与修改；拒绝在单独的事务里写审计。返回值是脱离草稿的普通数据。
- **系统上下文。** 模拟器以 `engine.run(null, …)` 运行，只能做车辆和外部服务会做的事（回执、事件、处理、质量与用途结果），不能调用需要授权的操作。角色页面从不伪造结果。
- **页面只显示能做的操作。** `useCan(action, target)` 用同一个 `authorize()` 判断是否有一条完整授权；只显示打得开的链接（`useCanOpen`，读不到的 Feature 只显示名称）。
- **入口与可访问性。** 登录页按角色分组，每个账号是一个按钮（可用键盘），显示它会进入的工作区；可按姓名、账号或角色搜索；停用或没有授权的账号单列并写明原因。账号菜单点击打开；可点击的行可用键盘到达；页面说明可在账号菜单里统一收起。模拟器自动运行时页头显示提示，点击即停。启动后只预加载账号能打开的页面，流程验收面板在打开时才加载。
- **导航上下文。** 登录时进入本浏览器里上次用过的工作区，否则进入未读警告、未读通知最多的工作区（都没有时：项目 → 团队 → 集成）；新账号打不开当前页面时回到工作台。通知按工作区投影，铃铛里列出其他工作区的未读数并可一键切换。分页写进路由（如 `features/<id>/validation`、`data/requests`、`integration/applicability`），通知与工作台直接打开要处理的分页。

## 4. 关键规则

### 4.1 授权

- 每条 grant 是完整授权：`role + workspaces + groups 或 scopes + envs`。操作要求**同一条** grant 满足全部条件，不拼接。
- 每个操作声明环境：`all`（平台级，需三个环境）、固定环境，或 `target`（对象自身的环境，如车辆、车辆组、事件）。
- 目标里的 `*` 只能被通配授权满足。“仅下发”测试授权可以下发，不能登记结果或确认 Verified。
- 平台运维不因管理账号获得业务或数据查询权限；最后一个完整的平台运维不能被移除。

### 4.2 配置编写与 DCL 接入

- 文件规格、策略、清单是内容寻址的不可变版本；提交只引用版本，未变化的内容复用。
- data_key 由平台生成且稳定；来源重叠交 DCL 判定；他组来源对无授权者隐藏。
- 敏感审核绑定内容签名，并按（业务分组、工作区）区分；最新一次决定生效。退回、绑定调整、撤销引用产生 `CHANGES_REQUESTED`，未变化的重新提交不能绕过。
- 跨组引用固定到所有者最近一次提交的版本；撤销引用使读取方 Feature 回到草稿。
- 提交时检查完整性、引用、处理模板与资源限制：单次采集就超出车型预算的策略在提交时被拦下（合并时还会按当时的预算再查一次）。

### 4.3 车辆与验证

- 每辆车只经过一个车辆组路由；期望配置与已生效配置分开，只有成功回执才改变已生效配置。
- 回执按 attempt 记录：同一 attempt 的相同回执是重放，不同内容拒绝，过期 attempt 拒绝。
- Feature 测试固定在当前提交，先仿真后实车；全部目标通过才能 Verified。研发 Feature 永远不能下发到量产车。
- 历史提交可以单独直接下发并登记结果（回归对比：提交没有被要求修改，仍通过提交检查，文件有现行的 DCL 批准）；结果只属于那个提交，不改变 Feature 的阶段，Verified 仍只看当前提交；团队测试申请只针对当前提交。

### 4.4 配置集成

- 只收集来源工作区里当前提交已 Verified 的 Feature。每个来源以自己的基线三方合并到目标版本；基线不同本身不是冲突。
- 冲突按字段记录并标出解决方：处理字段（格式、Schema、车端/云端处理）归 DCL，其余归业务。集成身份不代改内容。
- 合并后检查完整集合（策略捕获、处理绑定、引用固定版本与所有者定义一致）。
- DCL 确认绑定在预览摘要上；敏感文件须以合并后的内容获得批准。
- 冻结候选生成合并提交（内容与来源相同则复用来源提交）和完整车辆配置；来源 Feature 进入“已集成”。候选测试从零开始，只能下发到集成工作区的 testing 车辆组。冻结时再核对每个来源仍是本工作区的来源。
- 调整集成来源：来源还在未结束的合并预览、候选或征集中时不能移除（`SOURCE_IN_USE`）；每次调整记录前后的来源。组织节点改名、移动同样保留之前的名称与路径。
- 发布对话框列出配置摘要、DCL 处理确认、集成测试与每个软件版本的回滚目标，发布时引擎再查一遍。

### 4.5 正式发布与配置 OTA

- 发布复核：候选已集成验证、测试仍有效、DCL 确认仍匹配、目标版本未变化。DCL 策略集版本独立于整车软件版本（major.minor.patch，唯一且递增）。
- 适用的整车软件版本必须已登记，且每个版本都有通过的集成测试（测试记录车辆当时的软件版本）。发布不刷写软件，也不改变车辆已生效配置；新 Feature 默认以主线策略集为基线，修补旧策略集时可选它为基线（见 4.8）。
- 车辆按车型与实际整车版本解析到“适用该版本的最新正式发布”；版本未知或没有匹配时阻止量产下发，不回退到研发配置。
- OTA 只面向量产车辆组：逐车校验后整体通过或整体拒绝；先灰度第一批，**已下发的车辆全部回执成功后**才能扩大（`OTA_WAVE_PENDING`；第一批选了全部车辆时界面提示没有灰度）；任一失败自动暂停；恢复时失败车辆以新 attempt 重试，旧结果保留；回滚只回到每辆车之前成功、且仍适用其软件版本的正式配置，以新的 OTA 执行，回滚暂停后同样可以恢复。待放量的车辆视为占用。
- 量产车的软件变化后，未结束的 OTA 只在其策略集仍是新软件应运行的策略集（回滚：仍适用）时保留这辆车，否则车辆退出该 OTA（下发记录 `DROPPED`；暂停中的失败车辆同样退出，失败记录保留，OTA 可以恢复），迟到的回执被拒绝；所有车辆都退出时 OTA 记为已取消。

### 4.6 采集事件与数据查询

- 事件只来自车辆实际运行的配置，只采集该策略的 capture 文件，并固化正式版本、分组提交、策略版本、文件规格版本与处理版本；之后的变更不改变旧事件。
- 事件属于“把该配置下发到车上的工作区”与策略所属业务分组；查询在当前工作区内按 `event.query` 授权过滤，查询条件只能缩小范围。
- 训练数据可选用条件：处理完成、文件完整、质量 A/B、允许训练用途；未知不等于通过。训练结果与导出清单不含车辆身份与整车版本；导出时逐条重新检查。
- 解析失败由 DCL 以相同的固定版本重新处理，产物地址确定且不变。

### 4.7 策略集与整车软件版本

- 策略集与整车软件版本多对多。新增适用的软件版本要逐策略检查兼容性并通过集成测试，然后追加一条适用记录，策略集版本号不变。车辆按实际软件版本解析当前适用的策略集。
- 研发车组的基线跟随车辆的软件版本；分组自己的策略与开关只在显式发布时改变。
- 紧急停用一条策略：DCL 工程或配置发布申请，另一名配置发布批准。批准后生成去掉该策略的新策略集，只适用于原策略集当前生效的软件版本。

### 4.8 主线与同软件版本补丁

- 主线是最新的非补丁策略集；合并、新 Feature 的基线和新软件的适用检查都基于主线。
- 补丁（`Release.patchOf`）只针对仍对某些软件生效的旧策略集，只收 Verified 的 Feature，只服务目标策略集所服务的软件，版本号在目标的 major.minor 线内，不移动主线。合并预览、候选和“目标已变化”的门禁按线分开。
- 补丁里的 Feature 回到 Verified，必须再合入主线，或由配置集成写明理由关闭（反馈 `MAINLINE_DECLINED`）。
- 主线策略集要接管补丁服务的软件，必须带齐该补丁线的修复，包括紧急停用后生成的版本，否则 `PATCH_FIX_MISSING`。确认接管后，补丁不再服务该软件。

### 4.9 资源保护与采集预算

- DCL 工程按车型设定采集预算（CPU、车端缓存、存储写入、上传、每策略触发上限），单车可单独设置。车端代理按平台时钟的滚动一小时核算。
- HIGH 采集（核心业务、售后）超预算仍采集并标注。其他采集超出上传预算时排队；超出 CPU、存储写入或车端缓存，或单次就大于一小时的上传量时丢弃。只有车辆自己的触发计入洪峰上限，超过即抑制。被抑制和丢弃的采集不带数据，不进入查询。
- 合并时 DCL 逐策略检查资源：单次采集就超出车型预算的策略阻止确认处理集合（`RESOURCE_BUDGET`），高频时才会限流的只提示。
- 紧急停采：DCL 工程或配置发布（须在使用该车的工作区持有完整授权）写明原因即可暂停一辆车的采集。新触发立即拒绝；车辆确认后，车上未上传的采集丢弃。恢复同样需要原因和车辆确认。停采不改变策略集。

### 4.10 售后回捞与 Grader

- 业务方可为客户案例请求一辆车采集本组的一条策略，车辆下次连线时以 HIGH 执行。借出或报废的车辆拒绝请求，执行时再核对一次，不能执行就由平台取消并写明原因。
- 请求只对策略所属分组可见、可取消；挂起的请求阻止车辆环境变更与工作区归档。
- 售后请求未完成时，同一车辆上的 Grader 周期采集延后。处理完成后通知请求人；平台取消、采集未保留或处理失败时以警告提醒。

### 4.11 DCL 技术变更

- DCL 的技术修复不直接修改已发布的策略集，而是在业务分组上开技术分支（Feature 类型 `TECHNICAL`）。技术分支只能调整处理绑定，或把引用改到只改了绑定的新版本。它由 DCL 提交、本组测试验证，之后照常集成与发布。
- 技术变更不能退回给业务方，反馈发给 DCL；DCL 不能审核自己提交的敏感文件（`SELF_APPROVAL`）。

### 4.12 车辆、仿真与组织

- 借用：借入方的工作区管理员申请，写明车辆加入的车辆组和最后一天；使用方同意后，由车辆资源批准。到期会提醒，延期与归还都由人决定。下发设置云端配置，推送在车辆上线时送达；软件版本不匹配时可以修改策略，或经整车 OTA 更新车辆软件。
- 仿真运行配额由车辆资源按工作区设定：团队、个人与借入的仿真合计，配额不能低于正在运行的数量。报废的车辆不能恢复。
- 个人研发仿真只运行本人的草稿，试触发只本人可见；派生镜像只用于研发仿真。
- 车辆变更环境前，须先结束车辆组、下发与 OTA、预约、借用、运行中的仿真、处理中的事件与挂起的售后请求。车辆资源可以解除其他团队下发对一辆车的占用（写明原因，只取消这辆车，下发的其他车辆照常；这辆车不再是该版本的测试车，车辆组回到仍然有效的下发）。工作区、业务分组和组织节点只在没有未结事项时归档，可以恢复，不删除。工作区的未结事项还包括集成征集、适用性确认、团队测试申请和待批准的紧急停用；在它集成的策略集仍对某个软件版本生效时也不能归档（紧急停用与补丁在那里处理）。
- 每个账号都能只读查看组织树、工作区、业务分组与车型；授权规则与目录同步只对平台运维显示。工作区管理员在工作台查看本工作区的成员与授权。量产版本分布（集成版本 → 发布记录）按软件版本和正在运行的策略集计数，不显示车辆编号。
- 组织树来自公司目录同步。基础权限按组织规则授予，特殊权限显式授予；调岗会标记复核，离职会禁用账号。

### 4.13 集成征集与发布记录

整车集成版本像整车软件一样集成发布，只是交付物是 DCL 策略版本（`src/engine/calls.ts`）。

- **征集**：集成管理员（合并工作区的工作区管理员或配置集成，动作 `call.manage`）为目标整车集成版本发起集成征集。
  - 模块清单从工作区来源推出：团队工作区的业务组是叶子模块，域集成工作区是上层模块。
  - 软件还没登记时，平台建一个规划版本（`PLANNED`），软件清单从基线版本复制。
- **提交**：
  - 叶子模块由本组业务研发提交已验证的 Feature 提交，或"本次无变更"（`call.submitGroup`）。
  - 上层模块由域工作区管理员或域配置集成提交子系统发布，或"本次无变更"（`call.submitDomain`）。
  - 域工作区可以先开子征集收集本域各组，子征集的结果自动交回整车征集。
- **收齐与送测**：收齐后由配置集成生成集成预览（复用 `previewMerge`），经 DCL 处理确认后冻结。每一轮冻结的候选就是一个测试集成版本（"X89 1.2-T1"）。
  - 不通过时退回对应模块，当前一轮取消，下一轮合并新的提交。
  - 正在测试的一轮对提交人锁定（`CALL_ROUND_OPEN`），测试的就是征集记录的版本；要改动由集成管理员退回。集成管理员把模块设为不参加也会取消当前一轮；预览之后提交变了，预览不能再冻结（`CALL_ROUND_STALE`）。取消候选会同时停止它未回执的测试下发。
  - 送测后目标版本固定，因为测试证据绑定版本号；目标改到已有策略集的版本会被拒绝。
  - 整车征集正在测试时，子征集照常进行和发布，结果留在子征集并注明，整车征集退回该域模块后再提交。
  - 整车征集发布或按“本次无变更”结束、或某个域设为不参加时，未结束的子征集随之关闭；子征集已冻结的候选保留为本域候选，可照常发布。不参加的域不能开子征集。
- **规划版本**：研发和测试车、仿真镜像可以运行规划版本（预发布软件）；量产车不能，也不能为它开适用性确认。只有该征集的发布能列入它。
- **发布**：配置发布发布最后通过的一轮（`release.promote`），同时：
  - 规划版本转为已登记的整车集成版本；
  - 记录策略集 ↔ 整车集成版本的对应关系；
  - 把策略集导出为该版本 OTA 包内的 DCL 配置模块（`dclModule`）。
- **配置模块**：量产车的软件**换到**带模块的版本（车辆资源确认、域控上报或车辆签名上报；再次确认同一版本不算）时，配置随软件立即生效，不依赖云端推送，弱网或离线也能按正确策略采集。之后的补丁、紧急停用和适用性追加仍走云端配置 OTA。配置发布可以为外部登记的版本导出模块，或在补丁后更新模块。OTA 包带的是导出时的模块：另一个策略集接管该版本后，刷这个版本的车仍先运行包内模块，配置发布收到“包内模块已不是当前策略集”的提醒（`MODULE_OUTDATED`），更新模块并用配置 OTA 更新已刷的车。随模块生效的车辆没有下发记录，它的事件归车辆所在车辆组的工作区。量产车上报规划中的版本时按未登记处理，等版本发布并经车辆资源确认。
- **发布记录**（`src/engine/history.ts`）：按整车集成版本或按策略集，把征集、各轮测试、发布、适用关系、紧急停用、配置 OTA 的每一步（`Deployment.log`）和车辆软件变化串成时间线，并标出每一步之后生效的策略集。
- 软件版本按车型隔离（设计 v0.13"多车型版本"）。行业里同平台车型常共用软件基线，但集成、验证和 OTA 发布按车型分别进行。剧本 `multi-model` 走过 X90 的从空初始配置开发、两类测试、集成、发布 1.0.0、灰度失败重试与扩量，并核对 X89 的策略集、车辆与发布记录不变；来源、镜像、车辆、软件版本、候选与 OTA 都不能跨车型。
